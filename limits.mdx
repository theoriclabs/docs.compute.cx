These are the v0.1 customer limits. They can tighten without a docs deploy — treat API errors as authoritative.

## Runtime

| Limit | v0.1 |
|---|---|
| Function timeout | **10 minutes** default, **24 hours** maximum |
| Machine lifetime | Fresh machine per cold run; held machines default to 10 idle minutes and 8 hours after ready, maximum lifetime 24 hours |
| Concurrency | No per-account run or machine cap; one job at a time on each held machine |
| Create rate | None (no hourly create-rate cap) |

`timeout=` on `@app.function` is seconds. The CLI default is **600** unless the decorator or `--timeout` sets another value. The [workload guides](/guides/fine-tune) use a 30-minute decorator so image pull and a short train still finish.

Use [held machines](/cli/machines) to reuse a GPU, or [exec](/cli/exec) to run a shell command without logging into the machine.

## What you get

- One GPU SKU from `compute gpu list`.
- One process: your function.
- Logs and a JSON return value.
- A receipt after terminate.

## What you do not get

- A login shell on the machine.
- A region or instance-template picker.
- Persistent disks.
- A dashboard “Run” button — launch from the CLI.

## Admission

New creates can be refused when the account lacks enough available prepaid credit, reaches a spend limit, or no provider has capacity. Credit already held by other machines reduces what is available for new work. Accounts may keep several machines, model deployments and Tinker sessions live at once. Compute does not have a service-wide one-machine limit: different accounts are not serialized by a single Compute-wide machine slot. Provider capacity is not guaranteed.

If a run is refused, send the request id from the error to [Support](/support).
